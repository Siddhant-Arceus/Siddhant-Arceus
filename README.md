        ▼

# 🤝 How I Work With a Team

Software isn't built alone.

When contributing to a shared codebase, I like a workflow that keeps changes understandable and reviewable.

```text
              ┌─────────────┐
              │    Issue    │
              └──────┬──────┘
                     ↓
              ┌─────────────┐
              │   Discuss   │
              └──────┬──────┘
                     ↓
              ┌─────────────┐
              │    Build    │
              └──────┬──────┘
                     ↓
              ┌─────────────┐
              │    Test     │
              └──────┬──────┘
                     ↓
              ┌─────────────┐
              │    Review   │
              └──────┬──────┘
                     ↓
              ┌─────────────┐
              │    Merge    │
              └──────┬──────┘
                     ↓
              ┌─────────────┐
              │    Ship 🚀  │
              └─────────────┘
```

I value:

- Clear communication
- Small, understandable changes
- Code review
- Testing before merging
- Debugging systematically
- Keeping existing functionality intact
- Learning from other developers
- Sharing knowledge with the team

# 🧠 Development Philosophy

### 01 — Understand before changing

I prefer understanding the existing architecture before modifying a working system.

### 02 — Build for the actual user

A feature isn't finished just because the code works. The workflow should make sense to the person using it.

### 03 — Don't blindly follow the stack

```text
Problem
   ↓
Requirements
   ↓
Choose the right technology
   ↓
Build
   ↓
Measure
   ↓
Improve
```

### 04 — Learn while building

Real projects are often the best way to learn a technology.
